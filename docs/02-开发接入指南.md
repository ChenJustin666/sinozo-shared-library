# 开发接入指南

新服务使用 Kustomize，不再创建 `deploy/values*.yaml`。完整规范见 [Kustomize 部署方案](./Kustomize.md)。

## 1. 生成模板

```bash
./automation/init-service.sh <project> <service> java [port]
./automation/init-service.sh <project> <service> nodejs [port]
```

脚本生成 `Dockerfile`、唯一 `Jenkinsfile`、`deploy/kustomize/base` 以及 test/prod overlay。将完整业务目录复制到业务仓库；生产分支和 prod overlay 由 CODEOWNERS/保护分支限制修改权限。

## 2. 提交前检查

- Java 的 `pom.xml` 输出 `target/app.jar`（`<finalName>app</finalName>`）；Node.js 提交 `package-lock.json` 和前台运行的 `start` script。
- base、test overlay 的 `SERVICE_NAME` 已被初始化脚本替换；不要手工写镜像 tag，`APP_IMAGE` 由 CI 注入。
- Deployment、Service、`PORT`、探针的端口一致，Node.js 监听 `0.0.0.0`。
- 敏感配置使用 SealedSecret 密文或 ExternalSecret 引用，不要提交普通 Secret 或明文；Ingress 只放 overlay。

## 3. Jenkinsfile

本节 Jenkinsfile 同时作为 test/prod Job 的入口。test Job 可动态选择分支；prod Job 固定使用管理员配置的生产分支、生产 kubeconfig、白名单和人工审批，不允许开发修改 Job 权限或 Shared Library 版本。

```groovy
@Library('k8s-deploy-lib@main') _
k8sDeploy(
    projectName:  'adv',
    serviceName:  'ad-admin',
    serviceType:  'nodejs', // java | nodejs
    dockerImage:  'ad-admin',
    dockerCredId: 'docker-swr-cred',
)
```

Java 额外填写 `jdkTool`，Node.js 不需要 Jenkins 节点安装 Node。Job 名以 `-test` 或 `-prod` 结尾并与环境绑定；同一个 Jenkinsfile 可被两个 Job 使用，但 prod Job 的权限、分支和凭据由 Jenkins 管理员固定。`ACTION` 支持 `deploy`、`rollback`、`restart`。

## 4. 测试渲染

在业务仓库执行：

```bash
kubectl kustomize deploy/kustomize/overlays/test > /tmp/service-test.yaml
kubectl apply --dry-run=client -f /tmp/service-test.yaml
bash ./automation/kustomize-validate.sh deploy/kustomize/base deploy/kustomize/overlays/test
```

test 验证通过后，将相同 commit 合并到管理员指定的 `PROD_BRANCH`（例如 `master`），再由生产 `-prod` Job 发布。运维 review 通过保护分支和 CODEOWNERS 完成。不要让同一服务同时由 Helm 和 Kustomize 管理。
