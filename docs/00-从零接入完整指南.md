# 从零接入完整指南

本文给出平台、单服务和多服务仓库从零接入的完整顺序。当前标准是 Kustomize；旧 Helm 服务迁移前继续使用原流程，同一服务不能同时被两个引擎管理。

| 能力 | 方案 | 约束 |
| --- | --- | --- |
| 镜像版本 | 完整 Git Commit ID | `R<40位SHA>`，一次构建、多环境复用 |
| 流水线 | Jenkins + Shared Library | 每个业务仓库一个 Jenkinsfile；prod Job 的权限由 Jenkins 和 Shared Library 控制 |
| 配置管理 | Kustomize | Base + test/prod overlay，纯 YAML |
| 普通配置 | ConfigMap | test/prod 都进 Git，可审阅 |
| 敏感配置 | SealedSecret；已有中心密钥时 ExternalSecret | Git 只存密文或引用，不存普通 Secret |
| 环境隔离 | 同一 ACK 集群、不同 namespace | `<project>-test` 与 `<project>-prod` |

"都放到 Git" 指所有可部署的期望状态可版本化，也不等于把密钥明文放进 Git。当前推荐一个业务仓库包含 Dockerfile、base、test/prod overlay 和唯一 Jenkinsfile；生产分支及 prod overlay 由 CODEOWNERS 和保护规则控制。敏感值只保存 SealedSecret 密文或 ExternalSecret 引用。

## 1. 平台一次性准备

1. 测试和生产可共用同一 ACK 集群，默认 namespace 为 `<project>-test`、`<project>-prod`。首次部署时 Pipeline 会检查并自动创建，不要求平台提前手工创建；若安全基线不允许部署账号创建 namespace，也可由平台预建后把 `manageNamespace` 设为 `false`。
2. 安装 Sealed Secrets Controller，备份 controller 私钥，给开发提供加密公钥或受控的 `kubeseal` 通道。
3. 即使共用同一集群，也为 test/prod 创建不同 Kubernetes ServiceAccount 和两份 Secret file kubeconfig；test 账号不得访问 prod namespace。
4. 用平台管理员身份按 `kustomize/examples/common/deployer-rbac.example.yaml` 为两个环境 bootstrap Role/RoleBinding；若启用自动创建 namespace，再绑定文件末尾的可选 namespace ClusterRole。RBAC 不能由业务 Pipeline 自己提权。
5. Jenkins 全局环境变量设置 `K8S_CRED_TEST`、`K8S_CRED_PROD`、`PROD_BRANCH`、`DEVOPS_USERS`、`PROD_APPROVERS`；安装 Git Parameter plugin 以让 test Job 动态读取仓库分支。
6. 创建 SWR Username/Password 凭据 `docker-swr-cred`；`baselines/_global.yaml` 配置 registry 和 organization `sinozo`。
7. 配置 Shared Library `k8s-deploy-lib` 指向本仓库 `shared-library/`。首次部署时若目标 namespace 没有 `regcred`，Pipeline 会用该 Jenkins 凭据创建；已有 `regcred` 则直接复用。

安装 Sealed Secrets Controller 示例：

```bash
helm repo add sealed-secrets https://bitnami-labs.github.io/sealed-secrets
helm repo update
helm upgrade --install sealed-secrets sealed-secrets/sealed-secrets \
  --namespace kube-system --create-namespace
kubeseal --controller-name sealed-secrets \
  --controller-namespace kube-system --fetch-cert > sealed-secrets-public.pem
```

公钥可以提供给开发用于加密；controller 私钥不能离开运维控制范围，并应纳入加密备份与恢复演练。

生产凭据不能写在业务 Jenkinsfile。共享库强制从 `K8S_CRED_PROD` 取生产 kubeconfig，并要求生产分支和远端 commit 校验通过、触发者在运维白名单、人工审批完成。

Jenkins 安全边界：生产 Secret File 放入仅生产 Folder 可见的 Credentials，生产 Job 禁止开发修改 Pipeline script，生产 agent 不运行普通测试 Job；test/prod kubeconfig 分别绑定只能操作对应 namespace 的最小 RBAC。只隐藏凭据 ID 无法阻止开发绕过共享库。

Git 仓库门禁：生产 overlay 目录配置 CODEOWNERS，主分支禁止直接 push，PR 至少需运维 Owner 审批并通过 Kustomize 渲染/密钥扫描。Shared Library 使用受保护分支或发布 tag，生产 Job 不允许业务方选择未受信版本。具体设置见 [Git 与发布安全规范](./07-Git与发布安全规范.md)。

## 2. 单服务仓库

```bash
./automation/init-service.sh adv ad-gateway java
./automation/init-service.sh adv ad-admin nodejs
```

业务仓库提交：

```text
ad-gateway/
├── Dockerfile
├── Jenkinsfile
└── deploy/kustomize/
    ├── base/{deployment.yaml,service.yaml,kustomization.yaml}
    └── overlays/{test,prod}/{deployment-patch.yaml,configmap.yaml,kustomization.yaml}
```

业务仓库生产目录：

```text
deploy/kustomize/overlays/prod/
├── deployment-patch.yaml
├── configmap.yaml
├── sealed-secret.yaml
├── ingress.yaml               # 有外部入口时
└── kustomization.yaml
```

生产 Job 与测试 Job 使用同一个业务仓库 `Jenkinsfile`，但使用不同 Job 权限、kubeconfig、分支限制和审批规则。初始化脚本不再为每个服务生成 `Jenkinsfile.prod`；生产凭据仍只由 Jenkins Credentials 管理。

## 3. 多服务仓库

每个服务使用独立 test/prod Job、一个 Jenkinsfile、Dockerfile 和 Kustomize 目录：

```text
pic03/
├── services/
│   ├── pic03_admin_api/{Dockerfile,Jenkinsfile,deploy/kustomize/...}
│   ├── pic03_gateway/{Dockerfile,Jenkinsfile,deploy/kustomize/...}
│   ├── pic03_service/{Dockerfile,Jenkinsfile,deploy/kustomize/...}
│   └── pic03_web_api/{Dockerfile,Jenkinsfile,deploy/kustomize/...}
├── pom.xml
└── README.md
```

业务仓库 Jenkinsfile（test/prod 共用）：

```groovy
@Library('k8s-deploy-lib@main') _
k8sDeploy(
    projectName:  'pic03',
    serviceName:  'pic03-gateway',
    serviceType:  'java',
    dockerImage:  'pic03-gateway',
    dockerCredId: 'docker-swr-cred',
    subdirectory: 'services/pic03_gateway',
    jdkTool:      'jdk 17',
)
```

如果仓库用根 `pom.xml` 聚合构建，可以从服务目录指定父 POM：

```groovy
mavenGoals: '-f ../../pom.xml -pl services/pic03_gateway -am clean package -DskipTests'
```

服务 Dockerfile 仍位于 `services/pic03_gateway/`，复制该模块自己的 `target/app.jar`。test/prod Job 都指向业务仓库的同一个 `services/pic03_gateway/Jenkinsfile`；prod Job 通过管理员配置的 Job 权限、生产 kubeconfig、`PROD_BRANCH` 和共享库规则限制生产操作。业务代码不应在 Jenkinsfile 中写入生产凭据。

不要填写生产 kubeconfig。测试凭据也优先由 `K8S_CRED_TEST` 统一配置。

## 4. 配置与密钥

普通地址、开关、profile 放 ConfigMap 或 deployment patch。密码、AK/SK、token、证书和 `.dockerconfigjson` 不能明文进 Git。

创建生产 SealedSecret：

```bash
kubectl create secret generic pic03-gateway-runtime \
  --from-literal=NACOS_USERNAME='<user>' \
  --from-literal=NACOS_PASSWORD='<password>' \
  --from-literal=ACCESS_KEY='<ak>' \
  --from-literal=SECRET_KEY='<sk>' \
  -n pic03-prod --dry-run=client -o yaml \
  | kubeseal --controller-namespace kube-system --format yaml \
  > deploy/kustomize/overlays/prod/sealed-secret.yaml
```

然后把 `sealed-secret.yaml` 加入 prod `kustomization.yaml`。如果公司已有阿里云 KMS/Secrets Manager，使用 External Secrets 比 SealedSecrets 更适合集中轮换；Git 只保存 SecretStore/ExternalSecret 引用。

## 5. 前端 Ingress

Node.js + PM2 test 模板已经包含 Deployment、Service 和 ALB Ingress。必须修改 host；生产 host 和 TLS 在业务仓库 prod overlay 管理，但只能通过受保护 `PROD_BRANCH` 合并。不要使用 `cors-allow-origin: "*"` 配合 credentials，明确填写允许域名和 headers。API 路径转发到 Java gateway 时单独创建 Ingress，backend 指向 `<gateway>-svc`。

## 6. Java 监控与 SkyWalking

Java base 默认添加 Prometheus annotations，抓取 `/actuator/prometheus:8080`。应用必须启用 Spring Boot Actuator 与 Prometheus registry；未暴露接口时删除注解，避免无效抓取。

SkyWalking 属于可选环境 patch：使用 initContainer 将 agent 复制到 `emptyDir`，主容器挂载 agent，并在 `JAVA_OPTS` 添加 `-javaagent` 与 collector 地址。heapdump 使用独立 volume，生产需确认节点磁盘容量与回收策略，不要默认把大文件写入容器层。

## 7. 发布流程

1. feature 合并到测试分支，test Job 构建 `R<40位Git Commit ID>` 镜像并部署 `<project>-test`。
2. 测试通过后合并到管理员设置的 `PROD_BRANCH`（例如 master）。
3. 生产白名单人员触发名称以 `-prod` 结尾的独立 Job；共享库校验用户、管理员指定分支和远端 commit。
4. 生产只发布 test 已验证且已经进入 `PROD_BRANCH` 的镜像。推荐 fast-forward 合并，使 master HEAD 就是测试 commit（短显示值如 `28sf72ks9` 仅用于人工识别，实际使用完整 40 位 SHA），自动得到 `sinozo/<service>:R<完整SHA>`。共享库要求生产镜像 SHA 与 master 当前 HEAD 完全一致，不重新构建；若合并产生新的 merge commit，必须先在 test 验证该 merge commit 并生成对应镜像。
5. Pipeline 渲染 Kustomize、执行明文密钥校验和只读 diff；审批人查看差异并批准后才 apply，最后等待 rollout。
6. 部署对象写入 `image-commit`、`business-commit`、`ops-commit` 和 Jenkins build number 注解，可追溯镜像与业务 commit；使用业务仓库 prod overlay 时 `ops-commit` 与业务 commit 相同。

## 8. 上线检查

- `kubectl kustomize` 四套 test/prod overlay 渲染通过。
- Deployment selector 仍是 `app: <service>`，迁移旧 Helm 服务时不会修改 immutable selector。
- Java/Node 默认端口 8080；存量不同端口同时修改容器、Service、探针和应用监听。
- prod YAML 无 `Secret.stringData`、明文密码/AK/SK、真实 kubeconfig。
- `automation/kustomize-validate.sh` 校验通过；Pipeline 也会在 apply 前强制执行。
- SealedSecret namespace 与目标 namespace 一致，Controller 已生成同名 Secret。
- 前端 host/TLS、Java Prometheus path、资源 limits 和探针已验证。
