# 运维操作指南

当前部署引擎为 Kustomize + kubectl。Helm Chart 和 `helm_deploy.py` 只为尚未迁移的旧服务保留，新服务不再创建 values 文件。

## 1. Jenkins 节点要求

- Docker、Git；Java Job 需要已配置的 JDK/Maven 工具。
- `kubectl >= 1.21`，必须支持 `kubectl kustomize`、`diff`、`apply` 和 `rollout`。
- Git Parameter plugin，用于 test Job 动态读取业务仓库分支；prod Job 即使显示该参数，也会由共享库强制锁定为 `PROD_BRANCH`。
- Jenkins Shared Library 指向本仓库 `shared-library/`。
- kubeconfig 使用 Secret file，Docker 使用 Username/Password 凭据；Nacos Username/Password 只用于旧 Jenkins 注入模式。
- 目标集群安装并备份 Sealed Secrets Controller；没有中心密钥系统时，生产敏感配置依赖它解密。

管理员在 Jenkins 全局环境变量中定义集群凭据名称：

```text
K8S_CRED_TEST=<管理员定义的test凭据ID>
K8S_CRED_PROD=<管理员定义的prod凭据ID>
PROD_BRANCH=master
DEVOPS_USERS=ops-a,ops-b
PROD_APPROVERS=ops-lead,release-manager
```

test/prod 可以使用同一套 K8s 集群，但必须使用不同 ServiceAccount/不同 kubeconfig；namespace 按 `<project>-test`、`<project>-prod` 隔离，test 凭据的 RBAC 明确拒绝 prod namespace。`K8S_CRED_PROD` 只允许 Jenkins 管理员配置，业务 Jenkinsfile 中的 `kubeconfigCredId.prod` 会被忽略。Job 名以 `-test`、`-prod` 结尾并与环境绑定；test Job 可动态选择仓库分支，生产只能使用管理员设置的 `PROD_BRANCH`，Pipeline 会校验 workspace commit 与远端分支一致。prod 的 deploy/rollback/restart 都需白名单和人工审批。

生产 kubeconfig 凭据必须创建在仅生产 Job 可见的 Jenkins Folder Credentials 中，并通过 Matrix/Role Strategy 禁止开发修改生产 Job Pipeline、读取该 Folder 凭据或在生产 agent 上运行任意 Job。全局环境变量只保存凭据 ID，不等于权限隔离；凭据域、Job 权限和 K8s RBAC 才能防止开发绕过共享库另写 Pipeline。

业务仓库需对 `deploy/kustomize/overlays/prod/` 和 `PROD_BRANCH` 设置 CODEOWNERS 与保护分支，禁止直接 push；Shared Library 分支同样受保护。agent 无法直接读取 Library 资产时，由管理员配置 `K8S_DEPLOY_LIB_URL`、`K8S_DEPLOY_LIB_CRED`、`K8S_DEPLOY_LIB_BRANCH`，Pipeline 使用 Jenkins GitSCM 受管 checkout，不将 Git 凭据写入 remote URL。完整设置见 [Git 与发布安全规范](./07-Git与发布安全规范.md)。

生产 Job 的 Pipeline from SCM 指向业务仓库唯一 `Jenkinsfile`，但 Job 只允许平台/运维人员配置和触发。共享库会忽略业务 Jenkinsfile 中的生产 kubeconfig 覆盖，强制读取 Jenkins 管理员配置的 `K8S_CRED_PROD`，并强制 `PROD_BRANCH`、`-prod` Job、白名单和人工审批。

建议验证：

```bash
kubectl version --client
kubectl kustomize kustomize/examples/java/overlays/test >/tmp/java.yaml
kubectl kustomize kustomize/examples/nodejs-pm2/overlays/test >/tmp/node.yaml
```

## 2. 新服务上线

```bash
./automation/init-service.sh <project> <service> java [port]
./automation/init-service.sh <project> <service> nodejs [port]
```

脚本在临时目录生成业务文件，生产 overlay 也位于业务仓库：

```text
deploy/kustomize/overlays/prod/
```

运维必须 review 副本数、requests/limits、JVM/Node 环境变量、探针、端口、Ingress、调度和 PDB。生产配置随业务仓库 prod overlay 提交到受保护 `PROD_BRANCH`，Pipeline 读取该分支，不读取开发分支的生产配置。生产镜像 tag 必须与该分支当前 HEAD 的完整 commit 一致；test 验证的 commit 应通过 fast-forward 合并到 master，或在合并 commit 上重新测试。

## 3. 部署检查

Jenkins 会在 `.kustomize-render/` 合并业务 base 与目标 overlay，注入服务名、namespace、镜像和 Git 追溯注解，并完成源文件/渲染清单两次密钥检查。生产 deploy 先执行只读 `kubectl diff`，人工审批通过后使用同一 workspace 再次校验并 apply；非生产直接 diff/apply，最后等待 rollout。Pipeline 会先检查 namespace 和 `regcred`，存在则复用，不存在才创建；Docker 用户名和密码只通过 Jenkins Credentials 临时注入，不写入 Git。

常用命令：

```bash
kubectl get deploy,pod,svc,ingress -n <project>-<env>
kubectl describe deployment/<service> -n <project>-<env>
kubectl rollout status deployment/<service> -n <project>-<env> --timeout=300s
kubectl logs deployment/<service> -n <project>-<env> --tail=100
kubectl get events -n <project>-<env> --sort-by=.lastTimestamp
```

部署预览保存在 Jenkins 节点 `/data/backup/deploy-previews/<env>/`，默认保留 30 天。CI 的 `kubectl diff` 返回 1 表示存在差异，不是执行错误。

可追溯注解包含 `delivery.sinozo.com/image-commit`、`business-commit`、`ops-commit` 和 `build-number`。其中 image commit 对应实际部署的镜像 tag，business commit 对应业务 `PROD_BRANCH`；使用业务仓库 prod overlay 时 ops commit 为同一业务 commit（旧运维 overlay 模式才记录运维 commit）。

## 4. 回滚与重启

Jenkins `ACTION=rollback` 使用 Deployment revision：

```bash
kubectl rollout history deployment/<service> -n <project>-prod
kubectl rollout undo deployment/<service> -n <project>-prod
kubectl rollout undo deployment/<service> -n <project>-prod --to-revision=3
```

`ACTION=restart` 使用：

```bash
kubectl rollout restart deployment/<service> -n <project>-prod
```

Kustomize 没有 Helm release history。回滚只恢复 Deployment PodTemplate，不会回滚 Service、Ingress、ConfigMap 等其他对象；涉及这些资源时应回退 Git commit 后重新部署。

## 5. Secret 与权限

Pipeline 默认幂等管理目标 namespace 的 `regcred`，存在则跳过，不存在才用 Jenkins Docker 凭据创建；如果采用 ACK、SealedSecret 或 ExternalSecret 管理，可设置 `manageRegistrySecret: false`。Java 默认从 Git 中的 SealedSecret 读取 `<service>-runtime`；只有旧项目设置 `nacosSecretMode: 'jenkins'` 时才由 Jenkins 创建。其他 Secret 由运维维护，不提交明文。

Sealed Secrets 最小落地流程：

1. 集群安装 Bitnami Sealed Secrets Controller，并限制只有平台管理员读取 controller 私钥。
2. 用目标集群公钥执行 `kubeseal`，将生成的 `encryptedData` 提交到对应 prod overlay。
3. `kustomization.yaml` 将 `sealed-secret.yaml` 加入 resources；Controller 会生成同名普通 Secret。
4. 定期备份 controller 私钥；换集群或密钥轮换时重新 seal，旧密文不要直接复制到新集群。

RBAC 最少需要目标 namespace 内 Deployment、Service、Ingress、ConfigMap、HPA、PDB 的 get/list/create/patch/update，以及 Deployment rollout 所需权限。Sealed Secrets 模式授权 `sealedsecrets.bitnami.com`，External Secrets 模式授权 `externalsecrets.external-secrets.io`；启用默认 `manageRegistrySecret: true` 时还需要目标 namespace Secret 的 get/create/update/patch 权限。由于当前流程要求“没有 namespace 就创建”，`manageNamespace` 默认开启，需要额外的 namespace 创建权限；如果平台希望严格限制集群级权限，可预建 namespace 后将它关闭。test/prod 仍必须使用不同 kubeconfig 和 ServiceAccount。

可从 `kustomize/examples/common/deployer-rbac.example.yaml` 分别生成 test/prod 两套 namespaced Role/RoleBinding；文件末尾的 ClusterRole/ClusterRoleBinding 仅用于 `manageNamespace=true` 的自动创建模式。RBAC 本身由平台管理员 bootstrap，不由业务 Pipeline 自己提权；新 namespace 首次创建后，应由管理员补齐该 namespace 的 Role/RoleBinding，或让首次部署使用已具备这些权限的受控 kubeconfig。应用后用对应身份执行 `kubectl auth can-i --list -n <project>-<env>`，并确认 test 身份在 prod namespace 的所有写操作均返回 `no`。


## 6. Helm 服务迁移

1. 记录 `helm get manifest` 和当前资源清单。
2. 用初始化脚本生成 Kustomize 文件，保持 Deployment/Service 名、selector、端口不变。
3. 在 test 执行 `kubectl kustomize` 和 `kubectl diff`，重点检查 immutable selector 与 Service ClusterIP。
4. 停止该服务的 Helm Pipeline，再由 Kustomize apply；不要让两个工具并发管理。
5. prod 稳定后再归档旧 values。不要直接 `helm uninstall`，它会删除仍在运行的资源。

## 7. 常见故障

- `ImagePullBackOff`：检查 SWR project/tag、`regcred` 和凭据有效期。
- rollout 超时：检查 Pod events、资源配额、调度约束和探针。
- Java OOMKilled：降低 heap 百分比或增加 limit，查看 `logs --previous`。
- Node.js CrashLoop：确认 `npm start` 前台运行、生产依赖完整、监听 `0.0.0.0`。
- prod overlay 找不到：确认路径、大小写和文件已推送到 Shared Library 使用的分支。
