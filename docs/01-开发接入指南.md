# 开发接入指南

> 本文档面向开发人员，说明如何接入容器化部署

---

## 一、接入标准：全部接入 Nacos（统一标准）

### 核心原则

容器化后，Nacos 的接入**完全由运维通过 JAVA_OPTS 环境变量注入**，开发不需要在代码中写任何 Nacos 连接信息。

**运维注入的 JAVA_OPTS 示例：**
```
-Dspring.application.name=ad-gateway
-Dspring.profiles.active=test
-Dspring.cloud.nacos.config.server-addr=nacos.internal:8848
-Dspring.cloud.nacos.config.namespace=ad-gateway-test
-Dspring.cloud.nacos.config.username=nacos
-Dspring.cloud.nacos.config.password=xxx
-Dspring.cloud.nacos.discovery.server-addr=nacos.internal:8848
-Dspring.cloud.nacos.discovery.namespace=ad-gateway-test
-Xms512m -Xmx1024m
```

**开发只需要保证：**
1. 项目有 Nacos 依赖（spring-cloud-starter-alibaba-nacos-config/discovery）
2. 业务配置在 Nacos 控制台管理
3. 代码中**不要写死** Nacos 地址/密码

### 为什么不用 bootstrap.yml？

| 方式 | 问题 |
|------|------|
| bootstrap.yml 写死地址 | ❌ 换环境要改代码 |
| bootstrap.yml 用 ${} 占位 | ⚠️ 多一层间接，容易出错 |
| **纯 java-opts** | ✅ 代码零侵入，运维统一管理 |

Spring Cloud Alibaba 官方支持通过 JVM 系统属性（-D 参数）覆盖所有配置，优先级高于任何配置文件。所以：

```
✅ 保留 bootstrap.yml 也行（不影响），但里面不要写 Nacos 地址
✅ 没有 bootstrap.yml 也行，java-opts 会自动生效
❌ 不要在 bootstrap.yml 里写死 Nacos 地址和密码
```

## 二、当前服务分类与改造路径

| 类型 | 现状 | 改造要点 |
|------|------|----------|
| 第 1 类 | ECS 直跑，本地 application.yml | 加 Nacos 依赖 + 配置搬到 Nacos |
| 第 2 类 | 已 K8s + Nacos（java-opts） | ✅ 已完成，标准参考 |
| 第 3 类 | 未容器化，bootstrap.yml + Nacos | 删掉 bootstrap 中的地址，其他不动 |
| 第 4-6 类 | 防关联，本地配置 | 加 Nacos 依赖 + 配置搬 Nacos + 凭据挂载 |

## 三、按类型改造

### 3.1 第 3 类：已接 Nacos（最简单）

**现状：** bootstrap.yml 写死了 Nacos 地址

```yaml
# 现状（❌ 地址密码写死）
spring:
  cloud:
    nacos:
      username: nacos
      password: t#kz23492jHGz
      config:
        server-addr: http://172.26.0.20:18848
        namespace: 1be2a0d2-xxx
```

**改造：** 删掉 Nacos 连接信息，或者直接删掉 bootstrap.yml

```yaml
# 改造后（只保留 application name，其他全删）
spring:
  application:
    name: fc05-api
```

或者直接不要 bootstrap.yml，因为 `spring.application.name` 也会通过 java-opts 传入。

**就这么简单。** 运维通过 java-opts 注入所有 Nacos 参数。

### 3.2 第 1 类：未接 Nacos（需迁移配置）

**现状：** application.yml 几十上百行，数据库/Redis/Kafka 全在里面。

**改造步骤：**

#### Step 1：添加 Nacos 依赖

```xml
<dependency>
    <groupId>com.alibaba.cloud</groupId>
    <artifactId>spring-cloud-starter-alibaba-nacos-config</artifactId>
</dependency>
<dependency>
    <groupId>com.alibaba.cloud</groupId>
    <artifactId>spring-cloud-starter-alibaba-nacos-discovery</artifactId>
</dependency>
```

#### Step 2：将配置搬到 Nacos 控制台

```
Nacos → 配置管理 → 新建配置
  Data ID:   my-service.yml
  Group:     DEFAULT_GROUP
  Namespace: my-service-test（找运维创建）
  内容:      把 application.yml 的内容粘贴过来
```

#### Step 3：本地 application.yml 精简

```yaml
# 只保留端口（其他全在 Nacos）
server:
  port: 8080
```

#### Step 4：本地验证

```bash
# 用 java-opts 方式启动（模拟容器环境）
java -Dspring.application.name=my-service \
     -Dspring.cloud.nacos.config.server-addr=nacos-test:8848 \
     -Dspring.cloud.nacos.config.namespace=my-service-test \
     -Dspring.cloud.nacos.config.username=nacos \
     -Dspring.cloud.nacos.config.password=nacos \
     -Dspring.cloud.nacos.discovery.server-addr=nacos-test:8848 \
     -Dspring.cloud.nacos.discovery.namespace=my-service-test \
     -jar target/app.jar
```

确认能正常启动并连接数据库、Redis 等。

### 3.3 第 4-6 类：防关联服务

同第 1 类改造，额外：
- Firebase/GCP 凭据文件路径改为 `/app/credentials/`（运维通过 K8s Secret 挂载）
- 告知运维需要固定外网 IP

## 四、通用改造标准

### 4.1 打包

```xml
<!-- pom.xml 统一 jar 名 -->
<build>
    <finalName>app</finalName>
</build>
```

### 4.2 端口

统一 **8080**（不是 8080 的告知运维）。

### 4.3 健康探针

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
```

Nacos 配置中加：
```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,prometheus
```

验证：`curl http://localhost:8080/actuator/health` → `{"status":"UP"}`

### 4.4 监控

```xml
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-registry-prometheus</artifactId>
</dependency>
```

验证：`curl http://localhost:8080/actuator/prometheus`

### 4.5 日志

```
✅ 输出到 stdout
❌ 不写本地文件
```

### 4.6 Dockerfile

运维提供，放仓库根目录，不要改。

## 五、Nacos 配置管理

### Namespace 命名

```
格式：{service-name}-{env}
示例：ad-gateway-test, ad-gateway-prod
```

### 谁管什么

| 环境 | Nacos 配置 | 谁管 |
|------|-----------|------|
| test | 业务配置 | **开发可改** |
| prod | 业务配置 | **需通知运维** |

### 修改配置

```
测试环境：Nacos 控制台 → 修改 → 发布 → 自动刷新（不需要重新部署）
生产环境：先测试验证 → Nacos 生产控制台修改 → 通知运维
```

### 哪些放 Nacos vs 放 K8s

| 配置 | 放哪 | 谁管 |
|------|------|------|
| 数据库/Redis/Kafka/业务参数 | Nacos | 开发 |
| JVM 参数/CPU/内存/副本数 | K8s values | 运维 |
| Nacos 地址/命名空间 | K8s java-opts | 运维 |

## 七、常见问题

**Q: 启动慢会被杀？** → 不会，给 300 秒启动时间。

**Q: 还能用 bootstrap.yml 吗？** → 可以保留，但不要写 Nacos 地址。java-opts 优先级最高，会覆盖文件配置。

**Q: 本地开发不想每次写那么长的参数？** → 在 IDE 的 Run Configuration 里配置 VM options，保存一次就行。

**Q: 查看容器日志？** → `kubectl logs -f deployment/xxx -n project-test`

## 八、改造 Checklist

### 通用

```
□ pom.xml 添加 <finalName>app</finalName>
□ pom.xml 添加 spring-boot-starter-actuator
□ pom.xml 添加 micrometer-registry-prometheus
□ 端口 8080（或已告知运维）
□ /actuator/health 可访问
□ 日志输出 stdout
□ Dockerfile 放仓库根目录
□ 通知运维创建 Jenkins Job
```

### 未接 Nacos 的服务额外

```
□ 添加 Nacos config + discovery 依赖
□ 配置搬到 Nacos 控制台
□ 本地用 java-opts 方式验证能启动
□ 精简本地 application.yml（只留端口）
```

### 已接 Nacos 的服务额外

```
□ 删掉 bootstrap.yml 中的 Nacos 地址和密码
□ 确认 Namespace 命名符合规范
```

### 防关联服务额外

```
□ 凭据文件路径改为 /app/credentials/
□ 告知运维需要固定外网 IP
```

完成后告诉运维"可以接入了"。

## 九、改配置的 Git 工作流程

### 9.1 改测试/开发环境配置

当你需要调整测试环境的 CPU/内存/环境变量等配置时：

```bash
# 1. Clone k8s-deploy 仓库
git clone git@git.com:ops/k8s-deploy.git
cd k8s-deploy

# 2. 创建功能分支
git checkout -b feature/ad-gateway-increase-memory

# 3. 修改配置
vim projects/adv/test/ad-gateway/values-test.yaml

# 4. 提交并推送
git add projects/adv/test/ad-gateway/values-test.yaml
git commit -m "feat(adv/ad-gateway): 增加测试环境内存到 2Gi"
git push origin feature/ad-gateway-increase-memory

# 5. 创建 Merge Request
# 在 GitLab/GitHub 上创建 MR

# 6. 等待自动检查 + 自动 merge（测试环境）

# 7. 自动部署（5-10 分钟）
```

**详细流程请参考：** [03-Git工作流程与分支管理.md](03-Git工作流程与分支管理.md)

### 9.2 什么时候需要改 k8s-deploy 配置？

| 需求 | 改哪里 | 需要 MR 吗 |
|------|--------|-----------|
| 改数据库连接 | Nacos 控制台 | ❌ 不需要 |
| 改业务参数 | Nacos 控制台 | ❌ 不需要 |
| 改 CPU/内存 | k8s-deploy values | ✅ 需要提 MR |
| 改副本数 | k8s-deploy values | ✅ 需要提 MR |
| 改环境变量 | k8s-deploy values | ✅ 需要提 MR |
| 改 JVM 参数 | k8s-deploy values | ✅ 需要提 MR |

### 9.3 MR 多久会被合并？

```
测试/开发环境：
  提交 MR → CI 自动检查（1 分钟）→ 自动 merge → 自动部署（5 分钟）
  总计：5-10 分钟

生产环境：
  提交 MR → CI 自动检查 → 等待运维 approve → Merge → 运维手动部署
  总计：看运维响应速度（通常 30 分钟内）
```
