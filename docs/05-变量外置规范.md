# 变量外置规范

环境差异通过 Kustomize overlay 注入，代码和镜像不区分 test/prod。测试和生产的期望状态都进 Git，但不是都进同一个业务仓库。完整仓库门禁见 [Git 与发布安全规范](./07-Git与发布安全规范.md)。

| 内容 | Git 中的表达 | Owner |
| --- | --- | --- |
| 地址、开关、profile、副本和资源 | ConfigMap / patch 明文 | test 开发，prod 运维 |
| 密码、AK/SK、token、私钥、证书 | SealedSecret 密文 | 对应环境的密钥 Owner；生产提交到受保护 `PROD_BRANCH` |
| 中心密钥系统中的值 | ExternalSecret 引用，Git 不存值 | 密钥平台 |
| kubeconfig、Jenkins/SWR 凭据 | 不进 Git | Jenkins 管理员 |

## 非敏感配置

在 `configmap.yaml` 或环境 `deployment-patch.yaml` 中覆盖：

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: ad-gateway
spec:
  template:
    spec:
      containers:
        - name: app
          env:
            - name: SPRING_PROFILES_ACTIVE
              value: test
            - name: NACOS_SERVERS
              value: nacos-test.internal:8848
```

Java 可以在 `JAVA_OPTS` 使用系统属性，但地址、开关等优先使用独立 env，便于审阅和 diff。Node.js/PM2 服务可直接读取 Pod env；纯静态浏览器 bundle 必须在容器启动时生成 `config.js`，Pod env 不会自动进入已构建的 JS。

## 敏感配置

明文密码、token、证书和 `.dockerconfigjson` 不能提交 Git；Base64 只是编码，不是加密。禁止提交普通 `Secret`、`stringData` 或 Kustomize `secretGenerator`。

选型原则：

- 已有阿里云 KMS/Secrets Manager 或 Vault：优先 External Secrets，便于集中轮换、审计和撤销。
- 没有中心密钥系统：使用 Sealed Secrets，Git 只存 `encryptedData`。
- 同一个 Kubernetes Secret 只能有一个 Owner，不能同时由 SealedSecret、ExternalSecret 和 Jenkins 管理。

External Secrets 可参考 `kustomize/examples/common/external-secret.example.yaml`；先由平台建立 `SecretStore/ClusterSecretStore` 与阿里云访问权限，业务 overlay 只保存 remote key/property 引用。生产 SecretStore 应限制到生产密钥路径和目标 namespace，不能让测试 ServiceAccount 引用生产 remote key。

Java Nacos 用户名和密码默认由 SealedSecret/ExternalSecret 生成 `<service>-runtime`，base 通过可选 `envFrom` 引用。老项目可设置 `nacosSecretMode: 'jenkins'` 和 `nacosCredId`，但这是过渡兼容，不是新服务默认方案。

```yaml
envFrom:
  - secretRef:
      name: ad-gateway-runtime
      optional: true
```

## SealedSecret 流程

以生产 Nacos 凭据为例：

```bash
kubectl create secret generic ad-gateway-runtime \
  --from-literal=NACOS_USERNAME='<user>' \
  --from-literal=NACOS_PASSWORD='<password>' \
  -n adv-prod --dry-run=client -o yaml \
  | kubeseal --controller-namespace kube-system --format yaml \
  > deploy/kustomize/overlays/prod/sealed-secret.yaml
```

测试和生产密文都可以存在业务仓库对应 overlay（`deploy/kustomize/overlays/test/`、`deploy/kustomize/overlays/prod/`），但生产目录必须受保护分支和 CODEOWNERS 管理。然后将文件加入对应 `kustomization.yaml` 的 `resources`。

密文不是可以无限扩散的普通数据：默认 strict scope 与 Secret 名称、namespace 绑定；换 namespace/集群或 controller 密钥轮换后需重新 seal。Controller 私钥由运维加密备份并做恢复演练。

## 提交与审阅

- 业务仓库包含 base、test/prod overlay 和唯一 Jenkinsfile；生产 overlay 的修改必须经过运维 Owner 审批。
- prod overlay 使用保护分支、CODEOWNERS/审批人和 PR，禁止直接 push。
- 密钥变更必须记录负责人、生效时间和轮换/回退方案；离职、泄漏或权限收缩时立即轮换。
- CI 在渲染前后都运行 `automation/kustomize-validate.sh`，但这不替代仓库 secret scanning 和人工 review。
- Secret scanning 使用 Gitleaks、TruffleHog 或同类工具覆盖 PR diff 和 Git 历史；校验脚本无法发现藏在任意配置正文中的所有秘密。

## JVM 资源

`JAVA_OPTS` 与 Deployment memory limit 必须一起 review。推荐 `-XX:MaxRAMPercentage=70.0`，给 metaspace、线程栈和 native memory 留余量；固定 `-Xmx` 不得接近或超过容器 limit。

## 修改检查

```bash
bash ./automation/kustomize-validate.sh deploy/kustomize/base deploy/kustomize/overlays/test
kubectl kustomize deploy/kustomize/overlays/test > /tmp/rendered.yaml
bash ./automation/kustomize-validate.sh /tmp/rendered.yaml
kubectl apply --dry-run=client -f /tmp/rendered.yaml
```

检查渲染结果中只有目标环境的地址，且没有明文密钥、错误 namespace 或手写镜像 tag。
