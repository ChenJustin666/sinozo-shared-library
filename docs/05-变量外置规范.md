# 变量外置规范

> 本文档说明如何将应用配置从代码中解耦，通过 Helm values 注入到容器，实现一套代码多环境部署。  
> 适用于：Java 后端服务 + 前端服务

---

## 核心原则

**代码零改动，环境靠注入。**

- 应用代码不感知环境差异（不写 `if (env == "prod")`）
- 所有环境差异（Nacos 地址、DB 地址、日志级别等）通过环境变量注入
- test 配置由开发在 `deploy/values-test.yaml` 管理
- prod 配置由运维在 `baselines/projects/<proj>/<svc>/values-prod.yaml` 管理

---

## 一、Java 变量外置

### 1.1 注入链路

```
values-test.yaml
  └── java.opts: "-DNACOS_SERVERS=xxx -Dspring.profiles.active=test"
        │
        ▼ Helm 渲染
K8s Deployment
  └── env:
        - name: JAVA_OPTS
          value: "-DNACOS_SERVERS=xxx -Dspring.profiles.active=test"
        │
        ▼ Dockerfile 启动命令
exec java $JAVA_OPTS -jar /app/app.jar
```

`java.opts` 的所有内容会被 Helm 渲染成容器的 `JAVA_OPTS` 环境变量，启动命令直接读取。

### 1.2 application.yml 改造（传统项目接入必做）

将硬编码的配置改成读取环境变量：

**改造前（硬编码，不能上 CI/CD）：**
```yaml
spring:
  cloud:
    nacos:
      config:
        server-addr: 192.168.1.100:8848
        namespace: dev-namespace
```

**改造后（读环境变量，所有环境通用）：**
```yaml
spring:
  application:
    name: ${SPRING_APP_NAME:my-service}
  profiles:
    active: ${SPRING_PROFILES_ACTIVE:local}
  cloud:
    nacos:
      config:
        server-addr: ${NACOS_SERVERS:localhost:8848}
        namespace: ${NACOS_NAMESPACE:}
        group: ${NACOS_GROUP:DEFAULT_GROUP}
        username: ${NACOS_USERNAME:}
        password: ${NACOS_PASSWORD:}
      discovery:
        server-addr: ${NACOS_SERVERS:localhost:8848}
        namespace: ${NACOS_NAMESPACE:}
        username: ${NACOS_USERNAME:}
        password: ${NACOS_PASSWORD:}
```

> **语法**：`${ENV_VAR:defaultValue}`
> - `ENV_VAR` 是环境变量名
> - `defaultValue` 是本地开发时的默认值（K8s 里有注入时默认值不生效）
> - 冒号后面为空表示允许空字符串：`${NACOS_NAMESPACE:}`

### 1.3 JVM 参数写法规范

**推荐（生产级，基于容器内存比例）：**

```yaml
# deploy/values-test.yaml
java:
  enabled: true
  opts: >-
    -XX:+UseContainerSupport
    -XX:MaxRAMPercentage=72.0
    -XX:InitialRAMPercentage=30.0
    -XX:MaxMetaspaceSize=256m
    -XX:+UseG1GC
    -XX:MaxGCPauseMillis=200
    -XX:+HeapDumpOnOutOfMemoryError
    -XX:HeapDumpPath=/tmp/heapdump.hprof
    -Djava.security.egd=file:/dev/./urandom
    -Dfile.encoding=UTF-8
    -Dspring.application.name=my-service
    -Dspring.profiles.active=test
    -DNACOS_SERVERS=nacos-test.internal:8848
    -DNACOS_NAMESPACE=my-service-test
    -DNACOS_GROUP=DEFAULT_GROUP
```

关键参数说明：

| 参数 | 说明 | 备注 |
|------|------|------|
| `-XX:+UseContainerSupport` | JVM 感知容器 memory limit | Java 8u191+ / Java 11+ 支持 |
| `-XX:MaxRAMPercentage=72.0` | 堆最大 = limit 的 72% | 剩余给 Metaspace + 线程栈 + Direct Memory |
| `-XX:InitialRAMPercentage=30.0` | 初始堆 = limit 的 30% | 减少启动内存占用 |
| `-XX:MaxMetaspaceSize=256m` | Metaspace 上限 | 防止泄漏无限增长 |
| `-XX:+UseG1GC` | G1 垃圾收集器 | Java 9+ 默认，低延迟 |
| `-XX:HeapDumpOnOutOfMemoryError` | OOM 时 dump 堆 | 配合 HeapDumpPath 排查问题 |
| `-Djava.security.egd=file:/dev/./urandom` | 加快随机数生成 | 容器内 `/dev/random` 阻塞问题 |

> ⚠️ **不要同时写 `-Xms/-Xmx` 和 `-XX:MaxRAMPercentage`**，会冲突。

**test 环境资源紧张时，简化写法（-Xms/-Xmx 固定值）：**

```yaml
java:
  enabled: true
  opts: >-
    -Xms256m -Xmx512m
    -Dfile.encoding=UTF-8
    -Dspring.application.name=my-service
    -Dspring.profiles.active=test
    -DNACOS_SERVERS=nacos-test.internal:8848
    -DNACOS_NAMESPACE=my-service-test
```

确保 `-Xmx` < `resources.limits.memory`（留 200m+ 给 Metaspace）。

### 1.4 非敏感业务变量（env 注入）

不通过 JVM `-D` 参数，而是作为独立环境变量注入：

```yaml
# deploy/values-test.yaml
env:
  - name: LOG_LEVEL
    value: debug
  - name: SPRING_PROFILES_ACTIVE
    value: test
  - name: API_TIMEOUT_MS
    value: "5000"
  - name: FEATURE_FLAG_NEW_UI
    value: "true"
```

Java 代码读取：
```java
// 直接读环境变量
String logLevel = System.getenv("LOG_LEVEL");

// 通过 Spring 注入
@Value("${API_TIMEOUT_MS:3000}")
private int apiTimeoutMs;

// application.yml
app:
  timeout: ${API_TIMEOUT_MS:3000}
```

### 1.5 敏感变量（数据库密码、第三方 Key 等）

**不要写明文到任何 values.yaml**（会进 Git 历史）。

**推荐方案：运维预建 K8s Secret，values 里引用**

第一步：运维在 K8s 创建 Secret（仅运维操作，不进 Git）：
```bash
kubectl create secret generic my-service-secret \
  --from-literal=DB_PASSWORD=prod_password_xxx \
  --from-literal=REDIS_PASSWORD=redis_xxx \
  --from-literal=OSS_SECRET_KEY=oss_xxx \
  -n my-project-test
```

第二步：values-test.yaml 里用 `valueFrom` 引用：
```yaml
env:
  - name: DB_HOST
    value: mysql-test.internal      # 非敏感，可以明文
  - name: DB_PORT
    value: "3306"
  - name: DB_NAME
    value: my_service_test
  - name: DB_PASSWORD               # 敏感，从 Secret 引用
    valueFrom:
      secretKeyRef:
        name: my-service-secret
        key: DB_PASSWORD
  - name: REDIS_PASSWORD
    valueFrom:
      secretKeyRef:
        name: my-service-secret
        key: REDIS_PASSWORD
```

第三步：Java 代码读取（与普通环境变量一样）：
```yaml
# application.yml
spring:
  datasource:
    url: jdbc:mysql://${DB_HOST:localhost}:${DB_PORT:3306}/${DB_NAME:mydb}
    username: ${DB_USERNAME:root}
    password: ${DB_PASSWORD:}
```

### 1.6 ConfigMap 挂载（配置文件）

适合需要挂载配置文件到容器的场景（如 logback.xml、自定义 properties）：

```yaml
# deploy/values-test.yaml
configmap:
  enabled: true
  mountPath: /app/config          # 挂载到容器的路径
  data:
    logback.xml: |
      <?xml version="1.0" encoding="UTF-8"?>
      <configuration>
        <appender name="STDOUT" class="ch.qos.logback.core.ConsoleAppender">
          <encoder>
            <pattern>%d{yyyy-MM-dd HH:mm:ss} [%thread] %-5level %logger{36} - %msg%n</pattern>
          </encoder>
        </appender>
        <root level="${LOG_LEVEL:-INFO}">
          <appender-ref ref="STDOUT"/>
        </root>
      </configuration>

    app-ext.properties: |
      custom.timeout=5000
      custom.retry=3
```

JVM 参数里引用挂载的文件：
```yaml
java:
  opts: >-
    -Dlogging.config=/app/config/logback.xml
    -Dspring.config.additional-location=/app/config/
    ...其他参数
```

### 1.7 test vs prod 对照表

| 配置项 | test（开发管） | prod（运维管） |
|--------|--------------|--------------|
| Nacos 地址 | `nacos-test.internal:8848` | `nacos-prod.internal:8848` |
| Nacos 命名空间 | `my-service-test` | `my-service-prod` |
| Spring Profile | `test` | `prod` |
| JVM 堆 | `-Xms256m -Xmx512m` | `-XX:MaxRAMPercentage=72.0` |
| LOG_LEVEL | `debug` | `info` |
| 副本数 | `1` | `≥ 2` |
| 资源 limits | 按 test 节点调 | 按压测结果填 |

## 二、前端变量外置

前端的特殊性在于：**构建产物是静态文件**，构建完成后环境变量就"固化"了（除非运行时再注入）。

### 2.1 方案对比

| 方案 | 原理 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|---------|
| 构建时注入 | Dockerfile ARG → webpack/vite 打包 | 简单 | 一个镜像只能跑一个环境 | API 地址固定，不常变 |
| 运行时注入 | Nginx 启动时生成 config.js | 一个镜像跑所有环境 | 需要改前端读取方式 | 推荐，符合 12-Factor |

### 2.2 方案一：构建时注入

适合 API 地址在不同环境完全不同，且接受 test/prod 用不同镜像的场景。

**Dockerfile（多阶段构建，加 ARG）：**
```dockerfile
FROM node:18-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .

# 构建时从外部传入（vite 项目用 VITE_ 前缀；CRA 用 REACT_APP_ 前缀）
ARG VITE_API_BASE_URL=https://api-test.internal
ARG VITE_APP_ENV=test
ENV VITE_API_BASE_URL=${VITE_API_BASE_URL}
ENV VITE_APP_ENV=${VITE_APP_ENV}
RUN npm run build

FROM nginx:1.25-alpine
COPY --from=builder /app/dist /usr/share/nginx/html/
# ... nginx 配置
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
```

前端代码读取（Vite）：
```javascript
const apiBaseUrl = import.meta.env.VITE_API_BASE_URL;
```

> 局限：同一个 Docker 镜像只能用于构建时传入的那个环境，test 和 prod 是不同镜像。与平台的"一次构建，多环境复用"理念有冲突，适合过渡期使用。

### 2.3 方案二：运行时注入（推荐）

Nginx 容器启动时，先执行脚本生成包含配置的 `config.js`，前端页面加载时读取。

**第一步：自定义 Dockerfile（替换平台模板）**

```dockerfile
FROM nginx:1.25-alpine

COPY dist/ /usr/share/nginx/html/
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY docker-entrypoint.sh /docker-entrypoint.sh
RUN chmod +x /docker-entrypoint.sh && \
    chown -R nginx:nginx /usr/share/nginx/html

EXPOSE 80
ENTRYPOINT ["/docker-entrypoint.sh"]
CMD ["nginx", "-g", "daemon off;"]
```

**第二步：docker-entrypoint.sh（运行时生成 config.js）**

```bash
#!/bin/sh
set -e

# 运行时把容器环境变量写入前端可读的 config.js
cat > /usr/share/nginx/html/config.js <<EOF
window.__CONFIG__ = {
  API_BASE_URL: "${API_BASE_URL:-https://api-test.internal}",
  APP_ENV:      "${APP_ENV:-test}",
  VERSION:      "${APP_VERSION:-unknown}"
};
EOF

echo "✅ config.js 已生成:"
cat /usr/share/nginx/html/config.js

# 启动 nginx
exec "$@"
```

**第三步：index.html 引入 config.js**

```html
<head>
  <!-- 在所有其他 JS 之前引入，确保配置先加载 -->
  <script src="/config.js"></script>
</head>
```

**第四步：前端代码读取**

```javascript
// utils/config.js
const config = window.__CONFIG__ || {};

export const API_BASE_URL = config.API_BASE_URL || 'http://localhost:8080';
export const APP_ENV = config.APP_ENV || 'local';
```

```javascript
// api/request.js
import { API_BASE_URL } from '@/utils/config';

const request = axios.create({
  baseURL: API_BASE_URL,
  timeout: 10000,
});
```

**第五步：values-test.yaml 控制变量**

```yaml
# deploy/values-test.yaml
env:
  - name: API_BASE_URL
    value: https://api-test.internal
  - name: APP_ENV
    value: test

# prod 版本（运维仓库 values-prod.yaml）：
# env:
#   - name: API_BASE_URL
#     value: https://api.example.com
#   - name: APP_ENV
#     value: prod
```

同一个 Docker 镜像，test 和 prod 只是传入的 `env` 不同，完全符合平台"一次构建，多环境复用"的设计。

### 2.4 Vue / React 各自的构建时变量前缀

| 框架 | 环境变量前缀 | 读取方式 |
|------|------------|---------|
| Vite（Vue3/React） | `VITE_` | `import.meta.env.VITE_FOO` |
| Create React App | `REACT_APP_` | `process.env.REACT_APP_FOO` |
| Vue CLI | `VUE_APP_` | `process.env.VUE_APP_FOO` |
| Next.js | `NEXT_PUBLIC_` | `process.env.NEXT_PUBLIC_FOO` |

> 仅对构建时注入方案有效。运行时注入方案（window.__CONFIG__）不受此限制，任何框架通用。

## 三、常见问题

### Q1: Java 服务本地开发时环境变量怎么处理？

`application.yml` 使用 `${VAR:defaultValue}` 语法，本地运行时使用默认值，不影响开发体验。

```yaml
nacos:
  server-addr: ${NACOS_SERVERS:localhost:8848}    # 本地走 localhost
```

或者在 IDEA 的 Run Configuration → Environment variables 里设置本地值。

### Q2: JVM 内存设置了还是 OOM？

常见原因：Metaspace 超出 `-XX:MaxMetaspaceSize` 或 Direct Memory 泄漏。

检查步骤：
1. `kubectl describe pod <pod> -n <ns>` 看是不是 OOMKilled（Reason: OOMKilled）
2. 如果是，增大 `resources.limits.memory`，或降低 `MaxRAMPercentage`
3. 如果 Metaspace OOM，增大 `MaxMetaspaceSize`
4. 查看 `/tmp/heapdump.hprof`（如果挂了 PVC 或 emptyDir 才能取出）

### Q3: Nacos 连接超时 / 没有连上

排查顺序：
1. 检查 `java.opts` 里 `-DNACOS_SERVERS=` 的地址是否正确
2. 检查 K8s 网络，pod 是否能访问 Nacos 服务（service 名或 IP）
3. 检查 Nacos 命名空间是否存在（`-DNACOS_NAMESPACE=` 写的值）
4. 如果 Nacos 有认证，检查 `-DNACOS_USERNAME/-DNACOS_PASSWORD` 或 secretKeyRef

### Q4: 前端 window.__CONFIG__ 是 undefined

1. 检查 `index.html` 是否有 `<script src="/config.js"></script>` 且在其他 JS 之前
2. 检查 `docker-entrypoint.sh` 是否有执行权限（`chmod +x`）
3. 检查 Nginx 日志是否有报错：`kubectl logs <pod> -n <ns>`
4. 进容器确认文件是否生成：`kubectl exec -it <pod> -n <ns> -- cat /usr/share/nginx/html/config.js`

### Q5: 不想改 application.yml，有没有其他方式传 Nacos 地址？

可以通过 JVM 系统属性直接覆盖 Spring 配置，效果等同于改 yml：

```yaml
java:
  opts: >-
    -Dspring.cloud.nacos.config.server-addr=nacos-test.internal:8848
    -Dspring.cloud.nacos.config.namespace=my-service-test
    -Dspring.cloud.nacos.discovery.server-addr=nacos-test.internal:8848
    -Dspring.cloud.nacos.discovery.namespace=my-service-test
```

Spring 启动时 `-D` 参数优先级高于 application.yml，yml 里即使有硬编码地址也会被覆盖。这是传统项目接入的过渡方案，最终还是建议改 yml 读环境变量。
